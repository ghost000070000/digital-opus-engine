# API Friction Log

Every time building the demo (or an example/template) needed something the public `Opus` API couldn't cleanly do, that friction was recorded here and resolved in `engine/src/` before continuing.

---

## Dogfooding Discoveries & Public API Solutions (v0.1.0)

### 1. Camera Target Following
- **Demo Need**: Hovercraft driving required a third-person chase camera smoothly following the vehicle's position and orientation.
- **API Limitation**: `Camera` only provided Orbit mode controlled by mouse drag / arrow keys.
- **Workaround Rejected**: Manipulating camera internals (`camera.yaw`, `camera.target`) directly in demo tick code.
- **Public API Change**: Added `camera.setMode('chase' | 'orbit')`, `camera.setTarget(entity)`, and `camera.setChaseOptions({ distance, height, lerpSpeed, rotationLerpSpeed, lookAhead })` to `Camera`.
- **Result**: Demo game code calls `app.camera.setTarget(craft)`; target replacement and restart reset chase state to the live target while ordinary following remains smoothed.

### 2. Terrain Slope Collision & Sliding
- **Demo Need**: Hovercraft needed to drive over gentle island hills but slide smoothly along steep cliffs without penetrating ground or hard-stopping.
- **API Limitation**: `Physics` only provided `sampleWaveHeight` and `applyBuoyancy`.
- **Workaround Rejected**: Duplicating terrain height finite-difference math inside `21-game.js`.
- **Public API Change**: Added `Physics.resolveTerrainCollision(position, velocity, radius, terrainOpts)` returning `{ collided, grounded, steep, terrainHeight, slopeRadians, normal, correctedPosition, correctedVelocity }`.
- **Result**: Generic physics collision response is reusable across any Opus game.

### 3. Soft Map Boundary Pushback
- **Demo Need**: Hovercraft needed to stay within the island perimeter with soft pushback and HUD boundary warning.
- **API Limitation**: No boundary helper in engine physics; the first helper draft also accumulated inward velocity on every repeated edge sample.
- **Workaround Rejected**: Hard teleporting or custom demo boundary checks.
- **Public API Change**: Added `Physics.applyMapBoundary(position, velocity, radius, boundaryRadius)` returning pushback vectors and warning intensity.
- **Result**: Bounded, convergent pushback with stable warning intensity and no hard teleport.
- **Compatibility Impact**: Same return shape; pathological repeated edge calls no longer accelerate inward without bound.

### 4. Vehicle Engine Sound & Node Recycling
- **Demo Need**: Hovercraft needed dynamic engine hum pitching up/down based on speed and throttle.
- **API Limitation**: `AudioEngine` only supported single-shot `playBlip` and ambient noise drone. Creating new oscillators every frame caused audio glitches.
- **Workaround Rejected**: Direct Web Audio `AudioContext` node creation in demo code.
- **Public API Change**: Added `audio.startEngineHum()`, `audio.updateEngineHum(pitchRatio, volume)`, `audio.stopEngineHum()` with internal Web Audio node recycling.
- **Result**: Smooth engine hum with zero audio node allocations per frame.

### 5. Game HUD Primitives & Modals
- **Demo Need**: Crates counter, timer, title overlay, controls overlay, win/lose modal dialogs.
- **API Limitation**: `HUD` only had static FPS/Pause/Quality buttons.
- **Workaround Rejected**: Direct DOM manipulation in game script.
- **Public API Change**: Added `hud.addLabel`, `hud.addPanel`, `hud.showTitleCard`, `hud.showControlsOverlay`, `hud.showWinModal`, `hud.showLoseModal`, `hud.showWarning`.
- **Result**: Clean UI primitives managed entirely via public engine methods.

### 6. Mesh Creation Leaked the Rendering Context
- **Demo Need**: Assemble a procedural hovercraft and tutorial objects without bypassing the engine.
- **API Limitation**: Primitive factories required `app.gl`, which exposed the raw WebGL2 context and GPU objects.
- **Workaround Rejected**: Treating the renderer context as a supported game API.
- **Public API Change**: `Opus.Mesh.*` now returns shareable CPU-side descriptions; `App` privately materializes and caches GPU geometry when an entity enters its scene.
- **Result**: Demo, template, and examples create geometry without renderer access.
- **Compatibility Note**: Pre-0.1 preview calls such as `Opus.Mesh.cube(app.gl)` must drop the context argument.

### 7. Visible Water Sampling Was Static-Only
- **Demo Need**: Hover on the exact animated surface and blend smoothly across shorelines.
- **API Limitation**: Sampling required passing internal wave data and returned only a local displacement.
- **Workaround Rejected**: Copying shader wave equations into the game.
- **Public API Change**: Water handles provide world-space `sampleHeight` and `sampleSurface` methods; the latter also returns normal, intensity, and foam factor.
- **Result**: Gameplay and rendering use one wave definition.
- **Compatibility Note**: The static `Opus.Water.sampleHeight(handle, x, z, time)` remains supported but now returns world-space height.

### 8. Restart and Destruction Could Duplicate Work
- **Demo Need**: Repeated restarts, pause/resume, and teardown without stacked loops, listeners, audio, or particles.
- **API Limitation**: Input and resize listeners were anonymous, loop starts could queue duplicate frames, and GPU cleanup used cross-type WebGL probes that throw in Chromium before scene teardown completes.
- **Workaround Rejected**: Demo-side listener bookkeeping and page reloads.
- **Public API Change**: App-owned input/context/loop/audio/HUD/particle/GPU lifecycles now have idempotent cleanup; `onUpdate` and `onPauseChange` return unsubscribe functions.
- **Result**: Restart resets game objects in place and `app.destroy()` releases engine-owned work.
- **Compatibility Note**: `pause()` now pauses simulation while keeping the render loop alive so the public controls can resume it.

### 9. Seeded Mission Placement Needed Slope Queries
- **Demo Need**: Place five reachable crates and a delivery zone deterministically without steep or overlapping locations.
- **API Limitation**: Terrain exposed height but not a reusable public normal query.
- **Workaround Rejected**: Finite-difference sampling in demo code.
- **Public API Change**: Added `Terrain.sampleNormal` plus handle-level `sampleNormal`.
- **Result**: Placement rejection uses public terrain slope data and reproduces from one seed.
- **Compatibility Note**: Additive API; existing terrain sampling remains supported.

### 10. Fast Craft Could Skip Small Triggers
- **Demo Need**: Boosted movement must collect a crate even when one frame begins before and ends beyond its trigger sphere.
- **API Limitation**: `TriggerVolume.update(position)` only tested the final point.
- **Workaround Rejected**: Enlarging demo triggers or duplicating segment/sphere intersection math in the game.
- **Public API Change**: `TriggerVolume.update(position, previousPosition)` now performs a swept segment test while retaining the one-argument form.
- **Result**: Fast crossings emit one enter and one exit without duplicate scoring.
- **Compatibility Impact**: Additive optional argument; existing callers are unchanged.

### 11. Removed Entities Remained Usable as Camera Targets
- **Demo Need**: Restart replaces the hovercraft while chase mode is active without following stale scene state.
- **API Limitation**: Scene removal only spliced an array, and camera targets had no liveness contract.
- **Workaround Rejected**: Reaching into camera fields or maintaining demo-only tombstones.
- **Public API Change**: Entities expose a read-only-by-convention `destroyed` state; scene removal/clear destroys owned entities, and `Camera.setTarget` rejects destroyed targets and accepts `null`.
- **Result**: Target removal and replacement are deterministic and cannot produce stale chase transforms.
- **Compatibility Impact**: Removed entities are now terminal instead of reusable; callers should create a replacement entity.

### 12. Pause Advanced the Public Game Clock
- **Demo Need**: A 90-second mission and boost cooldown must not be consumed while paused.
- **API Limitation**: The update callback's `elapsed` value came from wall-clock loop time even though updates were paused.
- **Workaround Rejected**: Maintaining a second demo-owned clock that could drift from water and engine simulation.
- **Public API Change**: App callbacks and App-created water now share an App-owned simulation clock that advances only during active updates.
- **Result**: Pause/resume preserves timer, cooldown, animation, and visible/sampled water phase together.
- **Compatibility Impact**: `elapsed` now means simulation time, not wall time; this corrects the documented pause behavior.

## Editor Dogfooding Discoveries (v0 → v0.1)

### 13. No Way to Remove or Replace Terrain/Water After Creation
- **Editor Need**: Widening the palette to Terrain and Water means a placed instance's parameters (seed, size, radius) have to be editable in the inspector — which means regenerating the mesh live as the user drags a slider.
- **API Limitation**: `createTerrain`/`createWater` only ever add; nothing in the public API could remove or replace one, so a placed terrain was permanent for the life of the App.
- **Workaround Rejected**: Reaching into `app._terrains`/`app._waters` (private, and mangled away in the shipped bundle anyway) to splice a placed instance out.
- **Public API Change**: Added `App.removeTerrain(handle)` and `App.removeWater(handle)`, symmetric with `createTerrain`/`createWater`. Internally, a `WeakMap` (matching the existing `MESH_DATA`/`ENTITY_MESHES` pattern) maps the public handle to its private render record and GPU mesh, so removal can release VAOs/buffers without exposing renderer internals. A new `App._destroyMesh(mesh)` helper factors out the resource-deletion logic `destroy()` already had, reused by both.
- **Result**: The editor implements "edit terrain/water parameters" as remove-old + create-new-with-updated-opts, which reads as a live update to the user. Any game can now swap terrain/water at runtime too (e.g. loading a new area), not just the editor.
- **Result (validated)**: Create → remove → double-remove → remove-with-bogus-handle all produce correct behavior (clean success, then a clear `TypeError`-style message on misuse) — tested directly, not just by inspection.

### 14. No Way to Remove a Particle Emitter
- **Editor Need**: Consolidating the hovercraft into the editor's Play mode means spawning exhaust/spray/foam emitters when a play session starts and cleanly tearing them down (not just zeroing their rate) when it ends or restarts, so repeated play sessions don't accumulate dead emitters in `App`'s internal list.
- **API Limitation**: `createEmitter` only ever adds; there was no way to remove one, unlike terrain/water which already got `removeTerrain`/`removeWater` (#13).
- **Workaround Rejected**: Reaching into `app._emitters` (private) to splice one out, or just setting `rate = 0` forever and letting dead emitters pile up in the update loop.
- **Public API Change**: Added `App.removeEmitter(emitter)`, symmetric with the terrain/water removal methods added earlier — emitters have no per-instance GPU resources (they share the renderer's one particle buffer), so this is a simple list removal plus the same clear "not a valid handle" error on misuse.
- **Result**: A hovercraft's particle trail can be spawned and fully cleaned up each play session without leaking emitters.

### 15. Terrain Collision Ignored the Terrain's Own Position
- **Editor Need**: Expanding Crate Run to a second island (not at world origin) so there's more world to actually drive across.
- **API Limitation**: `Physics.resolveTerrainCollision` sampled height/normal using world x/z directly, never subtracting `terrainOpts.position` the way the per-instance `.sampleHeight()`/`.sampleNormal()` handles already did. It only ever worked because every terrain built with this engine so far (Delivery Run's island, the original single-island Crate Run) happened to sit at world origin — moving a second island away from (0,0,0) immediately exposed it: collision at an island's own center reported the ocean-floor height instead of real terrain height.
- **Workaround Rejected**: Translating world coordinates to local coordinates at the call site in the editor (and translating results back) — a workaround per caller, not a fix, and every other game hitting multi-terrain would rediscover the same bug.
- **Public API Change**: `resolveTerrainCollision` now offsets by `terrainOpts.position` (defaulting to origin when absent) before sampling height/normal, and adds the terrain's Y back into the returned height — matching the handle-level sampling convention exactly.
- **Result**: Collision is correct for terrain placed anywhere, not just at world origin. Caught by driving the actual consolidated game across a wider world, not by inspection — dogfooding a real capability (a second island) found a real, previously-dormant bug in an already-shipped API.

### 16. Terrain's Square Mesh Left a Flat "Platform" Beyond the Circular Island
- **Editor Need**: User feedback on the shipped 5-island Crate Run: land looked "underwater, not simulated properly" — a real visual defect, not a subjective nitpick.
- **API Limitation**: `createTerrainMesh` always generates a full `size x size` square grid, but `islandHeight` only shapes a circular landmass within it (via a radius-based falloff); everywhere beyond `radius` inside that square, height fell to `oceanFloor` — a perfectly flat constant, with zero variation. Rendered underwater (each island's flat skirt sits ~0.8 units below the water surface), a dead-flat square plate reads unmistakably as an artificial "platform," and since neighboring islands' square tiles sit close together (by design, for gameplay spacing), their flat skirts merge into one large, visibly rectangular submerged area.
- **Workaround Rejected**: Shrinking `size` relative to `radius` per terrain in the editor only shrinks the flat corners, it can't remove them (a circle inscribed in a square always leaves flat corners); increasing `radius` to fill the square would grow the actual island footprint enough to merge adjacent islands' landmasses, breaking the verified multi-island spacing this session already tuned and tested repeatedly.
- **Public API Change**: `islandHeight` now blends the area beyond `radius` toward a low-amplitude noise-based seafloor instead of a flat `oceanFloor` constant. Inside the island (`falloff === 1`) the new term cancels out exactly, so on-land height, crate/hazard spawn Y, and hover physics are provably unchanged — confirmed by re-running the same collision/grounding checks used for every prior island, all identical to before.
- **Result**: The submerged area around and between islands now reads as a naturally undulating seafloor instead of a manufactured flat plate, with zero change to any previously-verified on-land behavior. Physics and rendering share the same `islandHeight` call, so both stayed consistent automatically — no separate visual-only patch was needed.

### 17. No Way to Drive a Keyboard-Gated Game From Touch
- **Demo Need**: Touch support for *playing* an exported/shipped game (not editing one) — a phone or tablet has no physical keyboard, so anything gated on `input.isDown('KeyW')` (the hovercraft's entire movement scheme) had nothing to read.
- **API Limitation**: Camera orbit and click-based behaviors already worked on touch for free — orbit is driven by Pointer Events (unified across mouse/touch already), and taps synthesize a `click` event like any browser tap. But there was no way for an on-screen control to feed into the same key-state the driving code reads, short of reaching into `Input`'s private `keys`/`pressed` Sets directly.
- **Workaround Rejected**: Rewriting the hovercraft's movement code to read from a second, touch-specific input source alongside keyboard state — doubles the surface area to maintain and only fixes this one demo, not any other Opus game with the same keyboard-gated pattern.
- **Public API Change**: Added `Input.simulateKeyDown(code)` / `Input.simulateKeyUp(code)`, which drive the exact same Sets real key events do — so `isDown`/`wasPressed` can't tell the difference. Added `HUD.addTouchButton({ onStart, onEnd })` as a reusable "press and hold" primitive (existing `addButton`'s `onClick` only fires once a full click completes, which doesn't fit a held throttle/boost) wired through Pointer Events, so it works from touch, mouse, or pen on the same element.
- **Result**: Crate Run's own virtual D-pad + boost button (built in its own markup, since the editor runs with `hud: false`) needed zero changes to `updateCraftPhysics` — the exact same `input.isDown('KeyW')` calls the keyboard already drove now work from a finger. Verified a full physics-driven drive using only simulated touch input, and `HUD.addTouchButton` independently on a throwaway HUD-enabled instance (press/release counts exact, cleanup leaves no DOM node behind) for any other Opus game that uses the built-in HUD.

### 18. Editor's Own Object-Drag Was Silently Fighting the Camera (and Wasn't Touch-Capable at All)
- **Editor Need**: Making the editor itself usable on a touchscreen — placement, object-drag, marquee-select — not just exported gameplay.
- **API Limitation**: Two separate, real problems, both stemming from the editor's interaction code predating this concern. First: palette placement used HTML5 Drag-and-Drop (`draggable="true"` + `dragstart`/`drop`), which doesn't fire on touch in most mobile browsers at all — a palette a touch user can't drag from isn't no-code on a tablet. Second, and more surprising: `Input`'s own camera-orbit-drag listens on `pointerdown`/`pointermove`/`pointerup` (already Pointer Events, engine/src/04-input.js), while the editor's object-drag/marquee-select used legacy `mousedown`/`mousemove`/`mouseup` — a real physical click fires *both* event types on the same element, so every object-drag or marquee gesture was *also* silently accumulating into `Input`'s pending orbit-drag delta the whole time, priming the camera to jump on whatever frame next consumed it. Every prior test of drag-to-move/marquee-select in this session used synthetic `MouseEvent`s exclusively, so this was invisible until dispatching the matching `PointerEvent`s alongside them (matching what a real click actually produces) to test touch conversion — at which point `Input.dragDX/dragDY` showed the pending, un-consumed delta directly.
- **Workaround Rejected**: A touch-only parallel implementation bolted on next to the existing mouse-only one — doubles the interaction code to maintain and does nothing about the camera-conflict bug, which affects mouse users too.
- **Public API Change**: None needed for the camera fix — `Input.consumeDrag()` already existed; the editor just needed to call it every tick one of its own gestures is active, draining the accumulator before `Camera.update()` (registered earlier, so it always runs first on a given event) gets a chance to consume it. For placement, replaced HTML5 DnD entirely with a Pointer-Events-based implementation (a floating "ghost" element tracking `pointermove`, placement resolved on `pointerup` if released over the canvas) — one code path for mouse and touch, not two. Object-drag/marquee-select were converted from `mousedown`/`mousemove`/`mouseup` to the matching pointer events, with `activePointerId` tracking so a second concurrent pointer (a second finger, or any stray pointer) can't hijack or corrupt an in-progress gesture.
- **Result**: Verified extensively: palette placement end-to-end via dispatched Pointer Events (ghost follows, places on release over canvas, places nothing when released outside it); object-drag lands on the exact same point as before *and* leaves zero pending camera-drag delta afterward (confirmed both `dragDX`/`dragDY` at zero and `camera.yaw` unchanged, where before the fix the delta was confirmed non-zero and pending); marquee-select re-verified functionally identical under Pointer Events; a second concurrent pointer confirmed fully ignored mid-gesture; and `pointerType: 'touch'` events specifically confirmed to drive the identical code path. Full 21-crate win path re-verified unaffected throughout.

### 19. No Way to Bring a Real 3D Model Into the Editor
- **Editor Need**: Asset import — letting the no-code editor place a real, externally-authored 3D model, not just procedural primitives and hand-built custom meshes.
- **API Limitation**: `Opus.Mesh.fromArrays` already accepted flat position/normal/index arrays, so the *target* shape existed — nothing could produce that shape from an actual model file. glTF 2.0 is the natural format (open, JSON+binary, the de facto standard for real-time 3D interchange), but nothing in the engine could parse it.
- **Workaround Rejected**: A full-fidelity glTF importer (materials, textures, animations, skinning) — the renderer has no texture-sampling shader path at all (uniform per-entity color only) and `Entity` has no skinning, so parsing that data would produce fields nothing downstream could use. Pulling in a third-party glTF loader was never on the table (zero-dependency is a hard project constraint); a real parser had to be written from scratch either way, so the honest move was to scope it to what the engine can actually render.
- **Public API Change**: Added `Opus.Mesh.fromGLTF(input)` — accepts a JSON string (.gltf, buffers as base64 data URIs) or an ArrayBuffer (.glb binary container, or raw .gltf bytes); parses the node hierarchy, bakes each node's translation/rotation(quaternion)/scale into its vertices (flattening the whole scene into one mesh, since `Entity` supports one mesh per entity, not a scene graph), computes averaged per-vertex normals when a primitive omits NORMAL, and produces the same flat-array shape `fromArrays` already accepted. Geometry only, by design (see above). Throws a specific reason for anything unsupported (external `.bin` buffer references, non-indexed or non-triangle primitives, over 65535 vertices) rather than silently dropping data. Also added `Opus.Mesh.toArrays(mesh)` — the inverse of `fromArrays`, needed once the editor tried to serialize an imported mesh for Save/Load/Export: those all reuse the same `serializeScene`/`loadScene` pair Undo/Redo uses, and there was no way to get an imported mesh's geometry back out to persist it (no source file is kept around, and the raw arrays live in a private WeakMap by design). `toArrays` throws for cube/plane/grid/terrain descriptions, which are generated by the renderer at draw time and have no flat-array form to return.
- **Result**: Verified independently of the intentionally opaque public API (fromGLTF's result carries no inspectable data by design, matching fromArrays) by running the raw parser directly against known inputs: translation baking landed on the exact expected coordinates for every vertex (not approximately — bit-for-bit against hand-computed values); a 90-degree quaternion rotation cross-checked exactly against the engine's own already-trusted `Mat4.rotationY`; a real GLB binary container (spec-correct header/chunk layout, hand-built) parsed correctly including the missing-NORMAL fallback path; and four distinct error paths (non-indexed, unsupported primitive mode, external buffer reference, wrong input type) each failed with the intended specific message rather than a generic crash. In the editor: a full file-picker import (dispatched through the real `<input type=file>` `change` event, not a shortcut) correctly places a labeled, selectable, draggable item; critically, the mesh survives Undo/Redo and a real Save/Load round-trip through `localStorage` (confirmed the serialized record carries the exact vertex/index counts, and the reloaded scene's mesh is a genuine reconstruction, not a silent fallback to a plain cube) — this is the exact class of bug friction #15 and #18 were about, just for mesh identity instead of position. Full 21-crate win path re-verified unaffected.

## Major Expansion Batch — Bounded Fixes First (AUDIT.md High findings)

Before the expansion batch below, `AUDIT.md` (a full-codebase audit) had flagged three High-severity findings. Fixed all three first, kept bounded exactly as instructed, added targeted regression coverage, then moved on.

### 20. Custom Script Ran Unsandboxed From a Loaded Project With No Warning
- **Editor Need**: Loading or importing a project someone else built and shared must not silently run arbitrary JS the moment the player walks near an object.
- **API Limitation**: Not an engine gap — this is an editor-level trust boundary the engine has no opinion about (`new Function` executing Custom Script is a deliberate, documented design choice; the gap was specifically "loading someone else's file" vs. "authoring your own").
- **Workaround Rejected**: A real sandbox (iframe isolation, a JS subset interpreter, a permissions model) — far more than the actual risk warrants for a local single-page tool, and explicitly out of scope per the batch instructions ("do not build a giant sandbox").
- **Editor-only Change** (no public API surface needed): a session-level `scriptsTrusted` flag, defaulting to `true` for the live authoring session (building/testing your own project stays frictionless) and set to `false` whenever `loadProjectData` — the shared path behind both "Load Project" (localStorage) and the new "Import Project JSON" (file) — loads data containing any `action: 'script'` behavior. `runAction`'s script branch checks the flag before calling `new Function(...)` and toasts instead of running when untrusted; a banner with an "Enable Scripts" button lets the user explicitly opt in per loaded project. Node Graph is deliberately not gated — its nodes are a fixed, safe vocabulary with no eval, nothing to distrust.
- **Result**: Verified end to end: the shipped starter game's own Custom Script (crate collection) is unaffected (scripts trusted by default); loading a fake project containing a script behavior sets the flag false and shows the banner; the script is confirmed blocked via the real trigger-dispatch path (`runBehaviors`); clicking "Enable Scripts" flips the flag and the same script then runs. Captured as a permanent regression test in `tests/editor-smoke.html`.

### 21. glTF Import Allocated Before Checking Whether the File Was Reasonable
- **Editor Need**: Importing a model must fail cleanly on a malformed or hostile file, not hang the tab.
- **API Limitation**: `parseGLTFToArrays`'s only size guard (the 65,535-vertex ceiling `Opus.Mesh.fromArrays` requires) ran *after* every accessor for every primitive was already fully allocated and decoded — a crafted accessor claiming millions of elements would allocate tens-to-hundreds of MB and spin through a full decode loop before ever being rejected.
- **Workaround Rejected**: None needed a workaround — this was a straightforward missing early-exit, not an architectural gap.
- **Public API Change**: `readGLTFAccessor` (engine/src/21-gltf.js) now rejects any accessor with `count` over `GLTF_MAX_ACCESSOR_COUNT` (500,000 — generous headroom above the real ceiling so no legitimate model is affected) before allocating anything.
- **Result**: A crafted accessor claiming 50 million vertices now fails immediately with a specific message; a real small model still imports correctly (regression-checked in the same test). Added to `tests/public-api.test.js` as a permanent Node-runnable regression test — the first formal test coverage `Opus.Mesh.fromGLTF`/`toArrays` had (previously verified only manually during development, an AUDIT.md finding in its own right).

### 22. Node Graph Node IDs Could Collide After a Page Reload
- **Editor Need**: Reopening a previously-saved graph and adding a node must never collide with that graph's own existing node ids.
- **API Limitation**: Editor-only state bug, not an engine gap — `graphNodeIdCounter` is monotonic within one page session (safe there) but resets to 1 on every fresh load, while a saved project's graphs keep whatever ids they were created with.
- **Workaround Rejected**: A globally-unique id scheme (UUIDs) — correct but unnecessary churn for something scoped to fix with three lines, given node ids only ever need to be unique *within* their own graph, never across different items' graphs.
- **Editor-only Change**: `reconcileGraphNodeIdCounter(graph)`, called every time `openGraphEditor` opens a graph, scans that graph's existing node ids and bumps the counter past the highest one found.
- **Result**: Reproduced the exact bug precondition (counter reset to 1, opening a graph already containing `n1`/`n2`) and confirmed the counter reconciles to 3 and a new node gets `n3` with no duplicate ids. Regression-tested in `tests/editor-smoke.html`.

## Major Expansion Batch — Foundational Capability Tracks

### 23. Nothing Could Refer to "That Other Object" — Only to Itself
- **Editor Need**: Almost every new capability in this batch (target-reference actions, triggers, prefabs, Node Graph target fields) needs one object's behavior to name a *different* placed object and have that reference survive rename, duplication, Save/Load, Undo/Redo, and scene edits — not just act on `this`.
- **API Limitation**: `placed` items had no identity beyond their index in the array and a derived-on-the-fly display label (`itemLabel`, purely a function of kind/behaviors/position in the list) — nothing stable to store as a reference, and nothing to look a reference back up by.
- **Workaround Rejected**: Storing a live object reference (the `placed` entry itself) directly in another item's params — breaks the moment either side is serialized (Save/Load, Undo snapshot, Duplicate's deep clone via `cloneBehaviors`), since JSON has no notion of an object identity to preserve.
- **Editor-only Change** (foundational, no engine involvement — this is scene-graph bookkeeping, not rendering/physics): every `placed` item now gets a stable `id` (`objN`) assigned once, at creation, via a single choke point (`addPlaced`, which every `placed.push` call site now goes through) and never reassigned. `generateItemId`/`reconcileItemIdCounter` follow the exact same "counter resets on reload, reconcile against what's already loaded" shape as finding #22's `graphNodeIdCounter` fix. `findItemById(id)` resolves a reference, returning `undefined` for a deleted target rather than throwing — callers are expected to no-op gracefully (see #24). Items also gained an optional user-editable `.name` (inspector field, falls back to the existing derived `itemLabel` when unset via `itemDisplayName`).
- **Result**: Verified a full round trip: rename an item, duplicate it (clone gets a fresh id, not the original's), Save to localStorage, reload, Undo/Redo across several steps — id and name both survive every step, and duplicates never collide. `renderSceneList` was initially still calling the old raw `itemLabel` instead of the new `itemDisplayName`, caught by an explicit assertion during this verification (a real wiring bug, not a hypothetical) and fixed immediately. Full 21-crate win path re-verified unaffected.

### 24. The Fixed Action Dropdown and Node Graph Were Two Separate Implementations of the Same Behaviors
- **Editor Need**: A much larger action vocabulary (move/rotate/set-position/show-hide/enable-disable/destroy/change-color/counters, on top of the existing message/sound/win/lose/objective/boost/script) — but adding each one twice, once per system, guarantees the two drift (already true beforehand: Node Graph's `incrementCounter` had no fixed-dropdown equivalent at all).
- **API Limitation**: `runAction` (fixed dropdown) and `runGraphActionNode` (Node Graph) were independent `if/else` chains that each reimplemented every shared action (message/sound/win/lose/objective/boost) from scratch, reading from two different param shapes (`behavior.param`, a single string, vs. a graph node's own flat fields).
- **Workaround Rejected**: Adding new actions to both chains by hand, matched by convention — exactly the duplication already causing drift; nothing would catch the two falling out of sync again.
- **Editor-only Change**: introduced `ACTION_TYPES`, a single table keyed by action type (`label`, a `fields` list describing its params generically — `text`/`number`/`color`/`checkbox`/`target` — and one `exec(params, item)`), plus `executeAction(actionType, params, item)` as the one dispatch point. `runAction` and `runGraphActionNode` are now both thin wrappers: `runAction` converts a behavior's legacy `.param` string (kept, unchanged, for the original actions — existing saved Crate Run projects must keep loading exactly as before) or newer `.params` object into the params shape and calls `executeAction`; `runGraphActionNode` passes its node straight through, since a graph node's own fields are already flat in that same shape. `GRAPH_NODE_TYPES`'s action entries are now generated directly from `ACTION_TYPES` (condition nodes — AND/OR/Counter Reaches — stay graph-only, no fixed-dropdown equivalent exists). ### 31. Counter Reaches Only Compares One Direction — Found Building the Survival/Arena Stress Test
- **Editor Need**: A Lose condition gated on a health counter reaching 0 (health only ever decreases from a starting value) — surfaced while building Game C, this batch's Survival/Arena stress-test scene (a hunted-by-AI-enemies, collect-orbs-to-win game — see `games/survival-arena.json`).
- **API Limitation**: `counterReaches`'s condition is `value >= target`. Wired to `counterReaches(health, 0)` intending "health has run out," it instead evaluated true from the very first hit: with health starting at 3, `2 >= 0` is already true. The condition is correct and useful for what it was built for (a *climbing* counter — score, damage taken, crates collected — reaching a threshold), just structurally wrong for a *falling* one reaching a floor. Caught immediately by the dogfooding discipline this batch is built around: a real play-through (an AI enemy closing a real 10-unit gap over real elapsed time and tripping a real `TriggerVolume`) lost the game on the first hit instead of the third, rather than a synthetic test asserting the intended behavior in isolation.
- **Workaround Rejected**: Redesigning the game to use an increasing "damage taken" counter instead of a decreasing "health" counter — works, but only by avoiding the primitive rather than fixing the actual gap; "health counting down to zero" is too common a pattern (lives, ammo, timers) to make designers route around every time.
- **Public API Change**: None (editor/Node-Graph-only, no engine surface). Added `counterAtMost` (`value <= target`) as a sibling condition to `counterReaches`, sharing its rendering, port layout, and field metadata (both are leaf conditions with a `cond-out` port only, no `cond-in`) — a one-line addition to `evaluateConditionNode`, the node-type table, and the single `if` in `renderGraphNodeHTML` that special-cases leaf-vs-branching condition nodes.
- **Result**: Rebuilt the exact failing scenario with `counterAtMost(health, 0)` in place of `counterReaches(health, 0)` and confirmed the corrected sequence: health 3→2→1→0 across three hits, Lose firing only on the third (the one where `0 <= 0`), not the first. Re-verified with the real AI chase (not a manual trigger call) closing a 10-unit gap over ~1s of actual elapsed time and landing on the correct health value via a genuine `TriggerVolume` crossing. Full regression pass unaffected: 19/19 `public-api.test.js`, 3/3 `editor-smoke.html`, 21/21 crate win path.

### 35. No Way to Ship a Playable Game Without the Whole Editor Attached
- **Editor Need**: Bottleneck #4 from the final report: "Export Project" only ever produces a project JSON re-importable into the editor, not a self-contained file a player could open with no editor present.
- **API Limitation**: Not an engine gap — `editor/index.html` already boots straight into a playable scene (Crate Run) with the editor chrome hidden behind "Edit This Game," exactly the presentation a standalone export wants. The only thing missing was a way to make that SAME boot path load an arbitrary embedded project instead of the one hardcoded scene, and a way to produce a single file with no adjacent `dist/`/`src/` folder dependencies.
- **Workaround Rejected**: A separate, cut-down "player-only" runtime (re-implementing just enough of triggers/actions/craft-physics/HUD to play a game, without the editor). Rejected immediately: it would duplicate a large fraction of `01-editor.js` and drift from it the first time either one changed — exactly the "two parallel implementations" mistake finding #24 already fixed once this batch.
- **Public API Change**: None. **Editor-only Change**: the boot tail now checks for `window.__OPUS_EMBEDDED_PROJECT__` and calls `loadProjectData` with it (falling back to the existing `buildStarterGame()` when absent, so Crate Run's own boot is untouched). A new "Export Standalone Game" button fetches the engine bundle, `01-editor.js`, and `index.html`'s own source text, and inlines the first two as `<script>` blocks (not `<script src>`) into the third, with the current project (plus any Spawn-Prefab-referenced prefabs, reusing finding #34's `usedPrefabNames`) embedded as a preceding `<script>` setting that global — producing one genuinely self-contained, double-clickable HTML file.
- **A real bug found while verifying this, not while building it**: the first export attempt produced a file that failed to even parse. Separately, the replacement was also passed as a plain string rather than a function, which makes `String.replace` treat `$&`/`$$`/`` $` ``/`$'`/`$<n>` specially — a latent corruption risk for any embedded project data containing one of those sequences (e.g. inside a Custom Script param), even though it didn't happen to trigger on the specific test data used. Both fixed together: `escapeForInlineScript` replaces `</script` with `<\/script` (JS-semantically identical — a backslash before `/` in a string or comment is a no-op) before inlining, and both `.replace()` calls now use a replacer function instead of a string.
- **Result**: Verified by generating the exact export logic against real files (`dist/opus-engine.js`, `editor/src/01-editor.js`, `editor/index.html`, `games/survival-arena.json`) and opening the result in a real browser tab: it boots directly into Survival Arena (not Crate Run), `window.__OPUS_EMBEDDED_PROJECT__` present, health initializes to 3 via the real On Start behavior, collecting all 4 orbs fires a real Win, and the "Edit This Game" toggle is present and functional. Confirmed the fix reduced literal unescaped `</script` occurrences in the output from 9 (broken) to exactly 3 (the real, intentional closing tags). Full regression pass unaffected: 19/19 `public-api.test.js`, 3/3 `editor-smoke.html`, 21/21 crate win path.

### 36. No Object Could Physically Block the Craft — Bottleneck #1
- **Editor Need**: Bottleneck #1 from the final report: every placed cube is purely trigger-based, so nothing — not a wall, not a door — can physically stop the craft from driving through it. This directly shaped Game B's original design (a logic-gated goal instead of a real blocking door).
- **API Limitation**: `Physics.AABB` already existed (used for terrain picking) but had no collision *resolution* — only `containsPoint`/`intersectsAABB` queries, no way to push a mover back out. `resolveTerrainCollision` was the only precedent, and it's terrain-shaped (height-field, not a discrete box).
- **Workaround Rejected**: Full 3D sphere-vs-box resolution (resolving Y too) — unnecessary complexity for what this engine actually has: a hovering craft whose height is already fully managed by terrain/water sampling, completely independent of this. A horizontal-only (XZ-plane) push is the correct-scoped fix, not a corner-cut one.
- **Public API Change**: Added `Physics.resolveBoxCollision(position, velocity, radius, box)` (`engine/src/20-physics.js` + validated wrapper in `22-api.js`) — classic circle-vs-AABB resolution in the XZ plane, with a documented degenerate-case fallback (mover's center exactly inside the box, e.g. clipped through a thin wall in one frame: push out along the axis of least penetration). **Editor-only addition**: a `solid` flag on cube items (opt-in per object — existing crates/hazards/triggers stay pass-through, matching every game already built this batch), a "Solid (blocks movement)" inspector checkbox, and a check in `updateCraftPhysics` against every solid, *visible* item each frame. Checking `visible` alongside `solid` is deliberate, not incidental: it means Show/Hide Object (already-existing, finding #24) doubles as a complete door mechanic — hide it to open it — with no new action needed.

### 82. A Wander AI's Live Runtime Target Was Being Baked Directly Into the Saved Project File
- **Editor Need**: Signal Relay's two `DroneA`/`DroneB` guards, using a `wander` movement inside their `patrol` state -- saving the project (to pick up an unrelated field, `persistRuntimeState`) after the drones had been ticking live during an earlier Play session in the same editor tab.
- **API Limitation**: `serializeCubeRecord`'s own comment already correctly states that a State Machine's runtime caches "living inside each state's own `movement`" are deliberately NOT persisted -- but the actual code, `states: item.entity.ai.mode === 'stateMachine' ? item.entity.ai.states : undefined`, just assigned the LIVE `states` array by direct reference, with no stripping at all, contradicting its own comment. A Wander tick writes `ai.wanderTarget = new Opus.Vec3(...)` and `ai.wanderTimer` directly onto that same live `movement` object every frame; if a Save happened any time after a Wander AI had ticked even once in that session, the plain (already-mutated) `movement` object -- `wanderTarget` included -- got JSON-serialized straight into the project file. Loading that file back rebuilt `ai.states[*].movement` as a plain deserialized object with no Vec3 prototype at all, so the very next wander tick's `ai.wanderTarget.sub(pos)` threw `TypeError: ai.wanderTarget.sub is not a function` -- not a transient in-session leak like #81 above, but a genuine on-disk corruption of the authored project file itself.
- **Workaround Rejected**: Converting `wanderTarget` back into a real `Opus.Vec3` on load only -- would have stopped the crash but left the authored file itself permanently polluted with stale runtime coordinates that have nothing to do with the design, and done nothing for a project that gets Saved again before ever being reloaded.
- **Public/Editor API Change**: new `sanitizeAiStatesForSave(states)` helper (deep-clones `states`, strips `movement.wanderTarget`/`movement.wanderTimer`) called from both `serializeCubeRecord` (so Save never bakes runtime pollution in going forward) and the record-load path (so a file already polluted before this fix -- Signal Relay's own on-disk copy included -- loads safely and self-heals on the next Save).
- **Result**: reproduced live (`ai.wanderTarget.sub is not a function` thrown on load for a previously-saved-while-ticking project); a catalog-wide check found `forest-range.json` independently carrying the same on-disk pollution (2 occurrences, pre-existing, unrelated to this pass -- `arsenal-run.json`/`relic-frontier.json`/`silent-sector.json` use Wander but were not polluted), cleaned the same way (load, which now self-heals via the defensive load-side strip, then re-save). Re-verified fixed: a fresh Save of both Signal Relay and Forest Range contains no `wanderTarget` string at all; all five `wander`-using games in the full catalog re-loaded, entered Play, and ticked live for several real seconds with zero console errors after the fix.

## Post-Wave-9 Product Dogfood #2 (Foglight)

### 83. Five One-Click Palette Presets Placed a Sole Visible Mesh With `isTrigger: true`, Making Them Invisible in Play
- **Editor Need**: Foglight's own Mist Guardian enemy -- reaching for the palette's "👾 Enemy" preset as the obvious starting point for a contact-damage patrol enemy, the same way an author building any game with pickups/hazards would reach for "⭐ Collectible"/"➕ Health Pickup"/"☠ Damage Hazard"/"🏁 Checkpoint".
- **API Limitation**: `preparePlacedForPlay()` unconditionally hides any cube with `isTrigger: true` (`item.entity.visible = !item.isTrigger && ...`) -- correct and intentional for an authored, deliberately-invisible Trigger Volume marker. But `placeItem`'s own `collectible`/`healthPickup`/`damageHazard`/`checkpointPreset`/`enemy` branches each built their ONE AND ONLY visible mesh object with `isTrigger: true` set on it too -- meaning every one of these five one-click presets has been placing an object that goes invisible the instant Play starts, with no error, for as long as they've existed. `wireItemTrigger`'s own comment already correctly documents that `isTrigger` was never required for the enter/exit/stay overlap system at all ("an ordinary enter/exit/stay cube that ISN'T an authored Trigger Volume... keeps its existing sphere-1.5x-scale 'generous touch radius' behavior completely unchanged") -- the `Mine`/`Boost Pad` presets already correctly follow that pattern (no `isTrigger` at all); these five simply never did. This is the SAME bug class the Signal Relay pass already hit once in its own authored console objects (classified there as an authoring mistake, not an engine bug, and fixed by simply not setting `isTrigger` on them) -- but that was one author's own content; this one is baked into the engine's own stock preset library itself, reproduced by any author who reaches for any of these five presets, in any game.
- **Workaround Rejected**: Leaving `isTrigger` in place and instead special-casing `preparePlacedForPlay`'s visibility rule to exempt objects with `entity.ai` or specific tags -- would have papered over the symptom for the Enemy preset alone while leaving Collectible/Health Pickup/Damage Hazard/Checkpoint (none of which have `entity.ai`) exactly as broken, and would have made `isTrigger` mean something different and less predictable depending on what else an object happened to have.
- **Public/Editor API Change**: `isTrigger: true` (and the now-meaningless `triggerRepeat` that went with it, since none of these five ever relied on the one-shot semantics it only enables in combination with `isTrigger`) removed from all five presets' object literals in `placeItem`.
- **Result**: reproduced live (`placeItem('collectible', ...)` and `placeItem('enemy', ...)` each produced an object with `entity.visible === false` the instant `enterPlayMode()` ran, confirmed directly, not inferred), then re-verified fixed (both now correctly visible in Play; their own pickup/damage/repeat behavior unchanged, confirmed via the same `destroyObject`/`cooldown`-driven one-shot/repeat semantics they already relied on regardless of `isTrigger`).

### 84. A HUD Element's Inline Offset Style Always Included `left`/`top`, Silently Defeating Every Anchor Except Top-Left
- **Editor Need**: Foglight's own Objective Text HUD element, anchored `top-right` (distinct from the Health Bar's `top-left`) -- the ordinary, expected way to keep two HUD elements from overlapping.
- **API Limitation**: `renderHudLayer`'s per-element inline style was unconditionally `left:${el.offsetX||0}px;top:${el.offsetY||0}px` -- meant as a small additional nudge layered on top of whatever position the element's own `.hud-anchor-*` CSS class already computed (via `right`/`bottom`/`transform: translateX(-50%)` for the non-top-left anchors), per the code's own comment ("combined with the anchor class's own position below"). But an inline `left`/`top` always wins over a class's `right`/`bottom`/`transform` positioning (higher specificity, and `left` alone is enough to fully determine an absolutely-positioned box's horizontal position regardless of what `right` says) -- so with the default `offsetX`/`offsetY` of 0 (which nobody had ever needed to change, since 0 IS the "just use the anchor" case), EVERY element of EVERY anchor except literally `top-left` collapsed to the viewport's literal top-left corner. Found live: a `top-right`-anchored Objective Text rendered directly on top of a `top-left`-anchored Health Bar instead of in the opposite corner -- both elements' own `getBoundingClientRect()` read `left: 0, top: 0`, confirmed the class-based `right: 12px` was being computed but had zero effect.
- **Workaround Rejected**: Author-side -- manually setting a large negative-looking offsetX/offsetY per element to compensate -- would have required knowing the exact viewport width in advance (impossible for a responsive page) and defeated the entire point of a named "anchor" in the first place.
- **Public/Editor API Change**: the inline style now only emits `margin-left`/`margin-top` (never `left`/`top`), and only when an author has actually set a nonzero offset -- `margin` nudges an element from wherever its anchor already placed it without ever overriding `left`/`right`/`top`/`bottom`/`transform`, so every anchor now correctly renders at its own designed position by default, and the offset fields still work for the (left/top-anchored) cases they were originally useful for. A nonzero offset on a right/bottom/center-anchored element is a narrower, lower-impact edge case not fully solved by this fix -- documented, not chased, per this pass's own "fix the common case, don't chase every edge" scoping.
- **Result**: reproduced live (both elements' bounding rects at `(0,0)` regardless of configured anchor), then re-verified fixed (`top-left` element at `(12,12)` as its CSS class specifies; `top-right` element's right edge exactly `viewport width - 12`, confirmed against `window.innerWidth` directly) -- visually confirmed via screenshot: Health Bar top-left, Objective Text top-right, no overlap.

### 85. A Playable/Editable Export's `<title>` Fell Back to the Literal String "Digital Opus — Crate Run" When Project Meta's Own Title Field Was Empty
- **Editor Need**: Foglight's own clean-room Playable Export verification -- checking `document.title` inside the isolated `<iframe srcdoc>` realm, the same mandatory check every dogfood pass has run.
- **API Limitation**: `buildExportHTML`'s title-replacement fell back to the literal starter-demo name, `'Digital Opus — Crate Run'`, whenever `projectMeta.title` (a separate, easy-to-miss Project-tab metadata field, distinct from the much more discoverable and commonly-authored Start Screen's own Title field) was left empty -- which it was for Foglight, exactly as it likely has been for every dogfooded game before it, since nothing in this project's own history mentions ever setting it. The in-page Start Screen correctly showed "Foglight" throughout; only the browser tab's own `<title>` -- and therefore the file a player downloads/shares, an itch.io embed's tab, a bookmark -- carried a different, unrelated game's name instead.
- **Workaround Rejected**: none considered -- once the actual field being read (`projectMeta.title`, not `currentUiConfig.startScreen.title`) was identified, the fix is a straightforward better fallback chain, not a design tradeoff.
- **Public/Editor API Change**: the export's title fallback now tries `projectMeta.title`, then `currentUiConfig.startScreen.title` (a field essentially every real game already sets), then finally a neutral `'Digital Opus Game'` -- never a specific other game's name.
- **Result**: reproduced live (a Foglight clean-room export's `document.title` read literally `"Digital Opus — Crate Run"`), then re-verified fixed (`"Foglight"`, correctly pulled from the Start Screen title with no Project Meta title ever set); the actual Crate Run starter demo's own fresh-boot title was re-confirmed unaffected (`"Digital Opus — Crate Run"`, its own correct name, still shown -- this fix only changes what an EMPTY title falls back to, not any project that already resolves one).

## Game Catalog & Playable Builds

### 86. A New Editor Panel's Own Init Call Ran Inside Every Exported/Played Game, Making an Unexpected Network Request
- **Editor Need**: the game-catalog pass's own mandatory clean-room checks (`performance.getEntriesByType('resource')` must be empty for a genuinely self-contained Playable Export) -- the same check every prior dogfood pass has run, this time against a freshly-built `dist/games/foglight.html`.
- **API Limitation**: `buildExportHTML`/`composeExportHTML` embed `editor/src/01-editor.js`'s entire source verbatim into every export (a long-standing, deliberate design -- see Wave 6B's own "Edit This Game" requirement, which needs the full editor available inside an Editable Export). Any TOP-LEVEL init code in that file therefore runs inside every exported/played game too, not just the real dev editor -- something every prior addition to this file has had to keep in mind (e.g. `renderPrefabPalette()`'s own eager call), but the brand-new Games panel's own `loadGamesCatalog()` init call was added without that guard. The result: the instant ANY exported/played game loaded, it made a `fetch('../games/catalog.json')` network request -- harmless only by pure coincidence in this repo's own dev layout (that relative path happens to resolve to the real `dist/games/catalog.json` this same build produces), but a genuine violation of "no unexpected network dependency" for the single-file-portability case the catalog build's own clean-room test specifically exists to catch (a copied-elsewhere `.html` file would 404 on this fetch, silently, every time it loaded).
- **Workaround Rejected**: only fixing it for the games-catalog build specifically (e.g. stripping the Games panel's markup/script out of the exported HTML template at build time) -- would have meant the exported HTML template itself differs between "editor dev tool" and "export," reopening exactly the kind of two-tier duplication this whole pass was built to avoid (see the pass's own explicit "one export implementation" requirement).
- **Public/Editor API Change**: the Games panel's init (`loadGamesCatalog()`) is now gated behind `!window.__OPUS_EMBEDDED_PROJECT__` -- the exact flag every Playable/Editable Export already sets before the embedded editor script runs, reused rather than inventing a second "is this a real editor session" signal. The Games tab button itself is also hidden in that case, so an author who opens "Edit This Game" on an Editable Export doesn't see an inert tab.
- **Result**: reproduced live (`performance.getEntriesByType('resource')` returned `["http://localhost:8180/dist/games/catalog.json"]` for a freshly-loaded `foglight.html`, confirmed identical on a direct hard navigation with no launcher involved), then re-verified fixed (`[]`, zero network requests, across Foglight/Signal Relay/Arsenal Run); the genuine dev editor (opened directly, no embedded project) was re-confirmed to still show and correctly populate the Games tab.
